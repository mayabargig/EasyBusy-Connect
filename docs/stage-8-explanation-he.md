# שלב 8 - יציבות והכנה להגנה

## מטרת השלב

שלב 8 אינו מוסיף דרישת חובה חדשה. הוא מכין את המערכת להצגה יציבה מול המרצה:

- תיקון מעבר בין חשבונות בצ'אט.
- יצירת נתוני הדגמה עקביים.
- הסרת טקסטים זמניים.
- הכנת תהליך בדיקה מסודר.

## תיקון המעבר בין משתמשים

לפני התיקון, כאשר התנתקנו מתוך כתובת כגון `/chat/USER_ID`, ה-ProtectedRoute
שמר את הכתובת שממנה יצאנו. לאחר התחברות עם חשבון אחר, היישום ניסה לחזור לאותה
שיחה. השרת חסם זאת בצדק עם תשובת 403, משום שהשיחה לא הייתה שייכת לחשבון החדש.

כעת `handleLogout` מבצע שתי פעולות:

1. מוחק את הטוקן ואת המשתמש מה-AuthContext.
2. מעביר במפורש אל `/login` עם `replace: true`.

לכן מסלול פרטי של החשבון הקודם אינו נשמר בהיסטוריית הניווט.

## סקריפט ה-Seed

הקובץ `server/src/scripts/seed.js` מכין נתוני הדגמה הנמצאים ב-MongoDB:

- לקוחה אחת.
- שתי בעלות עסק בשתי קטגוריות.
- ארבעה שירותים.
- ארבעה פוסטים.
- שמונה תורים בחודשים ובסטטוסים שונים.
- שתי שיחות הכוללות ארבע הודעות.

השימוש במספר חודשים ובכמה סטטוסים מאפשר להדגים מיד גם את שני גרפי D3.

## מנגנוני הבטיחות

- הסקריפט נעצר אם `NODE_ENV=production`.
- הסקריפט פועל רק כאשר `ALLOW_DEMO_SEED=true`.
- הסיסמה נקראת מ-`DEMO_PASSWORD` ואינה נמצאת בקוד.
- הסיסמה חייבת להכיל לפחות עשרה תווים ולא יכולה להיות טקסט ברירת המחדל.
- בהרצה חוזרת נמחקים רק מסמכים הקשורים לחשבונות ה-Demo הייעודיים.
- משתמשים אמיתיים והתוכן שלהם אינם נמחקים.

## כיצד מריצים?

בקובץ `server/.env` מוסיפים זמנית:

```env
ALLOW_DEMO_SEED=true
DEMO_PASSWORD=סיסמה-מקומית-פרטית
```

לאחר מכן מריצים מתיקיית השורש:

```bash
npm run seed
```

לאחר שהנתונים נוצרו מחזירים את `ALLOW_DEMO_SEED` לערך `false`.

## שאלות אפשריות בהגנה

### למה ה-Seed אינו endpoint ב-Express?

אין סיבה שמשתמש באתר יוכל ליצור נתוני מערכת. פקודת פיתוח מקומית מצמצמת את
שטח התקיפה ומונעת הפעלה דרך הדפדפן.

### כיצד ההרצה החוזרת אינה יוצרת כפילויות?

המשתמשים מאותרים לפי כתובות Demo קבועות ומעודכנים במקום להיווצר מחדש. לאחר
מכן מוחלפים רק הפוסטים, התורים וההודעות המקושרים אליהם.

### למה התקבלה קודם שגיאת 403 בצ'אט?

הכתובת בדפדפן הכילה מזהה שיחה של החשבון הקודם. השרת בדק הרשאות ומנע גישה,
כפי שהוא אמור לעשות. התיקון בצד הלקוח מונע את הבקשה המיותרת מלכתחילה.
